# Removing Rust: the plan, and the compiler in cancho as the repository's main code

Status: **done on `main` (2026-11-22): no Rust compiler, no `cargo`, and the first release built from the seed alone is published (§5, Phase 6).** Written first as a design, before any move; the rest of this document keeps that record and is corrected in place. Epic [#491](https://github.com/alpibrusl/cancho/issues/491); the seven gaps it lacked are in
[the comment of 2026-11-05](https://github.com/alpibrusl/cancho/issues/491#issuecomment-6666808122). Numbers are from `main` at `c7435d6e`
(2026-11-05) by `wc -l` and by reading `docs/bootstrap.md`, `docs/cli-in-cancho.md` and `docs/standalone-cancho.md`; nothing was re-run. A
claim below that turns out false is corrected here, in place.

There is **one binary**, `cancho` (the Rust one, `crates/cancho/Cargo.toml`, deleted in Phase 5 step 7; the one that remains is built by `scripts/build-standalone.sh`). "All the binaries" therefore means: the release assets of every target
(`.github/workflows/release.yml`), `scripts/install.sh`, and the `cancho-rust` backup asset, which is retired.

## 2. Where it stands

**Nothing in the repository is written in Rust that the compiler needs.** The compiler in cancho (`compiler/`, 97 files, ~49,700 lines, plus ~17,400 of `runtime/`) is the only compiler. A standalone `cancho` written in it reproduces itself (stage 2 equals stage 3), and it is built from a committed seed of LLVM IR with `clang` alone (`seed/`, `scripts/build-standalone.sh --seed`, [`seed.md`](seed.md)). The CI gate is `scripts/gate.sh`, written in cancho and shell; the required checks of `main` are `gate (linux-x86_64)` and `gate (darwin-aarch64)`. The release is `release.yml`: stage 0 is the seed, stages 1 to 3 follow, stage 2 is published. The first release built that way from a tree with no Rust is `cancho-a8c5bc3bacc5221ad9f8492790b7b4df7d9ddf10` (2026-11-22, `--version` is `cancho 0.1.0`); the last release with a Rust-built compiler is `cancho-e4ea8b988b10d260f0ff8257843ed3423b09a06b`, whose `cancho-rust-*` assets stay downloadable for a project that needs Cranelift or WebAssembly (D2). What is **not** Rust-free on purpose: the optional Rust halves of the benchmarks (`benches/three/*.rs`, `tests/programs/f32_oracle.rs`) and the rustls peers of the TLS interop scripts. What is **not** cancho yet: three scripts of the gate use `python3` (`refusals.sh`, `release.sh`, `tty.sh`), and the measurement scripts under `scripts/*.py`.

## 3. Decisions (taken 2026-11-05 by the owner; recorded in #491)

**D1 remove the crates; D2 retire Cranelift and WebAssembly with the Rust compiler (#486; WebAssembly amended 2026-11-10); D3 `cancho test` replaces `cargo test`, no Rust shell; D4
Windows out of scope.** The options each decision chose among are kept below.

- **D1. Remove, not keep.** `standalone-cancho.md` §6 calls the crates "a backup". Keeping them means two implementations to hold equal for
  ever. This plan assumes removal; if D1 is "keep", only §5 phases 0 to 2 apply and the repository layout of §6 does not change.
- **D2. Cranelift and WebAssembly are retired with the Rust compiler** (#666 says so for Cranelift; it is open). WebAssembly was first decided as
  "port to `emit.cho` (#486)" (2026-11-05); **amended 2026-11-10 by the owner: skipped for now, so it is retired with the Rust compiler.** Both change what
  a release promises, so each needs a release note, and the one for WebAssembly says that `--target wasm32-*` goes with the Rust binary: a project that
  needs it (`cancho-industrial`, 5 files, `standalone-cancho.md` §1) keeps a pinned Rust-built release (the `cancho-rust` asset of the last release
  before deletion) or waits for a port that is no longer scheduled. What the amendment changes in this plan: `cancho-codegen-llvm` and `cancho-ir` no
  longer wait for a port, so phase 5 deletes them straight after `cancho-codegen` and is shorter; the nine programs of `tests/reject` named `*_on_wasi`
  (refused by the Rust compiler only, `tests/reject.known`) are fixtures of a retired target, and are removed with it in the phase 5 PR that deletes the
  last crate that refuses them, with the entry of `wasm_target::build_refuses_too_not_only_check` in `.github/selfhost-known-differences.txt`;
  `authority --target wasm32-wasip1` is **already** in the compiler in cancho (`authwasi.cho`, `cli-in-cancho.md` slice (c)), so there is nothing to port or drop there: it reports on programs for a target that no build writes, and stays until someone decides to remove it. Reversible: if a port is wanted
  later it is a new decision with `docs/wasm.md` (W0.2–W2c) as its design, and the crates would have to be kept until it lands.
- **D3. The oracle's shape.** The 726 conformance tests run `cancho` and compare output. Two ways: (a) `cancho test` runs them as cancho
  programs with a `.expected` file each, no Rust anywhere; (b) a small Rust shell stays as the test runner only. (a) is the goal; (b) is
  allowed as a stage, with a date for its end.
- **D4. Windows.** Neither compiler targets it (#490). Decide before the release pipeline is rewritten, since it is a column in the matrix.

## 4. Gates: what must be true before each crate is deleted

A crate is deleted in a PR by itself, only when:
1. nothing in the workspace names it (`cargo tree -i CRATE` is empty; checked by CI);
2. the standalone `cancho` built **without** it passes the whole oracle, on all three targets (macOS aarch64, Linux x86-64, Linux aarch64);
3. the goldens (§5, phase 1) stand in for what it was the oracle of;
4. the fixed point holds: stage 2 equals stage 3, built from the seed.

**The open pull requests (a gate for every deletion and for the move).** No crate is deleted, and the `selfhost` directory of `examples` is not moved, while an open
pull request touches what the change deletes or moves: each is merged, closed, or rebased onto the new layout first, by its owner's word, and the
deleting pull request lists the check. The check is `gh pr list --state open` with `gh pr diff N --name-only` filtered on the paths; measured
2026-11-05 on 19 open pull requests:

| touches | pull requests |
|---|---|
| `crates/` | #681 (8 files, draft), #700, #699 (draft), #494 (draft), #476 (draft, 3), #413 (draft, 3) |
| `compiler/` | #681 (22, draft), #701 (8), #698 (4), #697 (6), #696 (5), #694 (3), #692 (6), #690 (5), #699 (1) |
| neither | #695, #693, #689, #666, #656, #350 |

The drafts that are old (#413, #476, #494) either rebase or are closed before phase 5; closing is the owner's decision, not this plan's. The six
`vcs-native` pull requests (#690 to #692, #694, #696, #698, #701) are the continuing port of `cancho vcs` (#680) and keep landing in
`compiler`, so the move of phase 6 waits for that series to pause, or it is rebased once.

## 5. Phases

**Phase 0: housekeeping and the decisions (days).** Take D1 to D4. Correct the stale numbers (#491's body, `bootstrap.md` "22,000 lines",
the conflict marker at `docs/cli-in-cancho.md:619-620`). Close the primitives that block ports: #684 to #688.

**Phase 1: the seed and the goldens (#488; the seed's design is [`seed.md`](seed.md)).** (a) A committed seed: the LLVM IR or object of the standalone compiler for each target with
a recorded BLAKE3, reproducible from `cancho.files` plus `clang`; a script `scripts/reseed.sh` that rebuilds it and a CI check that the
seed rebuilds itself to the same bytes. (b) Golden outputs: for every test whose expected value is "what the Rust compiler writes" (parity,
identities, IR, refusals), record the output once and compare to the file. After this the Rust compiler is no longer the only way to know
the answer.

**Phase 2: close the compiler's own gaps (#482, #485, #487, #665).** The remaining CLI commands, the runtime text generated from the Rust
crates (`build.rs`) moved to checked-in files with a test that regenerates them, the device verbs, `authority`, `--emit obj`, `-l`/`-L`.
`vcs` V1 (#680) in cancho. Done when `CANCHO_COMPILER=auto` skips nothing in `.github/selfhost-known-differences.txt` that is not a retired
backend.

**Phase 3: the gate moves (D3; designed in [`gate.md`](gate.md)).** `cancho test` runs the conformance programs; the Rust test shell shrinks file by file as each moves
(a test file is moved or deleted, never both left). `tests/files.rs`'s 2,000-line check becomes a script or a cancho program.
`CLAUDE.md`, `CONTRIBUTING.md` and `AGENTS.md` change from `cargo fmt/clippy/test` to the new gate **in the same PR** that makes the new gate
required, not before.

**Phase 4: the release without Rust.** `release.yml` builds from the seed (stage 0 = the seed, not a Rust build), runs stages 1 to 3,
publishes stage 2, and the smoke test (`install.sh` then build hello) stays. The `cancho-rust` backup asset is last published in the release
before deletion and named in its notes. *Done in the workflow (2026-11-18):* `release.yml` builds no Rust unless the dispatch input `rust_backup`
is set, which is done once, with `publish`, for that last release.

## 7. Risks, and what each is measured by

- **No oracle but the compiler itself.** A bug present in the seed and in the compiler passes the fixed point. Measured by: the goldens
  (phase 1) and the reject corpus (339 of 339 today), kept and not regenerated from the new compiler.
- **Seed rot.** A seed nobody rebuilds stops matching the source. The rule, and what CI checks, is in [`seed.md`](seed.md) §5.
- **Code quality.** Measured once and again with `-O2` (`bootstrap.md`: within 1.3 on 36 rows; the P-256 rows 1.03 to 1.05). The
  `tls-perf` job now builds the compiler in cancho from the seed and runs the guard with it (phase 4, 2026-11-18), against the baseline the
  Rust compiler's code recorded. *Corrected:* this paragraph said the baseline "must be re-recorded with the compiler in cancho before phase 5".
  It need not be: the guard compares instruction counts against fixed numbers and does not need the Rust compiler to exist; the compiler in
  cancho is within 1.05 of them, inside the 1.3 the guard allows. Re-recording would only move the baseline by that 5 %, and needs valgrind on
  each machine of the file (`linux-x86_64` is a CI runner this repository cannot reproduce locally); it is done when a primitive gets cheaper by
  more than the guard's reciprocal and the guard asks for it.
- **Compile time and `clang`.** 33 s a stage for the 77-file command line. The compiler still needs `clang` (#489); say so in the install docs.
- **Windows.** Out of scope until D4.
- **Flaky tests** (`dup2`, #592) are noise in the gates; fix or quarantine them in phase 0.

*`$CLANG` is not read, on purpose (2026-11-19).* The compiler in cancho (`compiler`, every stage built from the seed) names the clang it runs with `--clang PATH` (an absolute path) or else `/usr/bin/clang`; it does not read `$CLANG`, which only the retired Rust compiler did. A cancho program has no `getenv`, `cli.cho` releases its `Ffi`, and a program it starts has only the environment it is given (`docs/reach.md` §3.1, `docs/cli-in-cancho.md` §22), and that stance is kept: no `Ffi("libc")` `getenv` and no `env_get` builtin was added for this. Consequence for scripts and CI: the shell reads `$CLANG` and passes `--clang "$clang"` (`scripts/build-standalone.sh`, `reseed.sh`, `seed-ir-fixed-point.sh`, `scripts/fuzz_afl.py`, `release.yml`), and a test that must observe the clang used passes `--clang WRAPPER` (`tests/commands/declared_intrinsics.sh`). Writing `CLANG=… cancho build …` with the native compiler picks `/usr/bin/clang` and ignores the variable, on macOS and on Linux alike. (`README.md` and `docs/standalone-cancho.md` already said so; the two older documents that said `CLANG` names another clang, `package-system.md` and `tls-assurance.md`, are corrected in place.)
