# Routing `cancho vcs` through the command line in cancho: `init`, `log`, `show`, `branch`, `status`

Status: **design; nothing here is built.** Written before the code, as `CONTRIBUTING.md` asks. It is the step 2 of the order in `docs/vcs-native.md` §7 ("route `log`, `show`, `status`,
`branch` and `init` from `cli.cho` so the repository form exists as a command"), and part of #680. Claims are marked **[measured]** (run for this document, 2026-11-11, Linux x86-64),
**[read]** (taken from the named file, not run) or **[choice]** (a decision this document proposes). Decisions for the owner are in §6.

## 1. What a person gets today **[measured]**

The command line in cancho (`examples/selfhost/cli.cho`, built from `cancho.files` by the compiler in cancho) and the Rust `cancho`, run in the same repository: one the Rust command made with
`vcs init` and one `vcs record`.

| `vcs …` | the Rust command | the command line in cancho |
|---|---|---|
| `log` | the document of changes (`{"changes": […]}`) | ``nothing published yet at `.cancho-vcs` ``, exit 0: **the manifest log, in a repository** |
| `log --limit 1` | the document, one change | ``unknown option `--limit` `` and the whole usage, exit 2 |
| `status`, `show`, `init`, `branch` | their documents | the generic usage of `fmt`, `print`, `ingest`, exit 2 |

So the 15 commands are not "missing": the five this document is about are *unreachable*, and one of them, `log`, answers **wrongly and with success**. A script that runs `cancho vcs log` in a
repository and checks the exit status passes on the cancho-written command and reads the wrong thing.

## 2. What exists **[read]**

* **The libraries, written and checked against a store the Rust command wrote** (`docs/vcs-native.md` §6): `vcsrepo.log_command`, `show_command`, `status_command` (documents, byte for byte),
  `vcsstore.init`, `vcsstore.read_ref`, `vcsstore.update_ref` (compare-and-swap), `vcsrepo.resolve` (revisions: `HEAD`, `@`, ids and prefixes, branches and tags, `~N`). `vcsstorectl.cho` is a
  test command over them ("Not a user command", its header), which prints `refused TAG` and not the Rust refusal document.
* **What `branch` needs and the store does not have:** `list_refs` and `delete_ref` (`cancho-vcs/src/refs.rs:167`, `:186`). `vcsstore.cho` has `read_ref` and `update_ref` only.
* **`cli.cho` routes the registry side of `vcs`** (`log` as the manifest log, `lock`, `fetch`, `resolve`, `publish`, `sync`) in `cli.cho:57-72`, and nothing of the repository side.
* **A walk upward from the current directory already exists in cancho:** `cliproject.find_project` looks for `cancho.toml` in the current directory and the ones above it with the whole-file
  `Fs("")` the command line holds, the directory from `/bin/pwd` run through `Exec` (`cliproject.cho:24`, `:79`). **This answers the one item `docs/vcs-native.md` §7 left unverified** (whether the
  `Fs` the command line holds reaches the directories above the current one): it does.
* **How the Rust command routes** (`vcs_cli.rs:93`): `log` is the manifest log when `--store` is named or **no repository is in reach**; every other repository command is `vcs_repo::dispatch`.
  Discovery is `Repo::open`: canonicalize the start (`--repo` or `.`), look for `.cancho/vcs/format` there and in each parent, refuse an unknown format, and refuse `not-a-repository` at the top
  (`cancho-vcs/src/repo.rs:110`). Every command accepts `--output json`, `--repo` and `--dry-run`; an unknown option is a usage error (`crates/cancho/src/vcs_args.rs:68`).
* **The output**: one pretty JSON document on stdout, keys sorted, `{"ok": true, "command": …, …}` or `{"ok": false, "command": …, "refused": {"tag", "message", …}}`; a refusal exits 1, an
  environment failure 3 (`vcs_args.rs:78`, `main.rs:221`). `docs/vcs-cli.md` §4 says "text is a rendering of the same result"; the code prints the document in both cases, so **the document is what
  parity means**.
* **The oracle after Rust is checked in:** `tests/vcs_fixtures/pins/` holds 38 documents (init, status, log, show, branch, 5 refusals, …) from the Rust command, and `crates/cancho/tests/vcs_repo.rs` compares the
  Rust command with them with the root normalised (`normalise`, line 86).

## 3. The bootstrap rule decides the order **[read]**

`docs/seed.md` §5: *the compiler's sources may use a builtin only when the committed seed already compiles it; a change that needs a newer compiler than the seed is two pull requests: the compiler
change, then the reseed, and only then the code that uses it.* Adding a module to `cancho.files` puts it in the compiler's own sources.

* The seed is **older than #760**: it does not know `dir_rmdir`, `dir_symlink` or `dir_readlink` (edition 12). `vcsscan.cho` now reads links with `dir_readlink` (#761).
* **`vcsrepo.cho` imports `vcsscan.cho`** (`vcsrepo.cho:21`: for `tag` and for `status_command`). So *any* routing that imports `vcsrepo` (`log` and `show` included) pulls `dir_readlink` into the
  compiler's sources, and the seed chain (check 1 of `seed.md` §5) fails.
* Two ways out: wait for a reseed, or **keep the modules `log` and `show` need free of `vcsscan`** (a split of `vcsrepo.cho`, §5 R0). The reseed is not free: three seeds of about 1.9 MB each go
  into the history (`seed/`: 1,914,753, 1,920,732 and 1,919,655 bytes), and the macOS seed has to be written on a Mac: `.github/workflows/reseed.yml` runs on the two Linux targets only
  (**[read]**; whether a macOS runner could be added is not looked at).

## 4. The decisions

**D1. The routing is the Rust command's. [choice, from §2]** `vcs log` is the manifest log when `--store` is named or no repository is in reach, the repository log otherwise; `init`, `status`,
`show`, `branch` (and later `diff`, `record`, …) go to the repository commands. Unknown subcommands keep the cancho command line's usage error.

**D2. Discovery, and the one difference it has. [choice]** The start is `--repo PATH` or the current directory (`cliproject.current_directory`); the walk upward is `cliproject`'s `ancestor`
(a path is cut at its last `/`, so no `..` is ever written: an `Fs` traps on one); `.cancho/vcs/format` is read with the `Fs("")`; a format other than `cancho-vcs 1` and the top of the tree are the two
refusals of `Repo::open`, with its messages. **The difference:** the Rust command *canonicalizes* the start (it resolves links) and the command line in cancho has no `realpath` (`vcs-native.md` §7
item 4, #686). The current directory comes from `/bin/pwd` with no environment, which is the physical one, so a command run with no `--repo` agrees. A `--repo PATH` that holds a link is taken as written,
and the `root` that `init` and the refusals print differs from the Rust command's then. The tests normalise `root` as `crates/cancho/tests/vcs_repo.rs` does; the difference is said in the sentence of `--repo`, and not hidden.

**D3. One new module for the repository side, and none of it in `clivcs.cho`. [choice]** `clivcs.cho` is the manifest side (`publish`, `log --store`); the repository side is `clivcsrepo.cho`:
the option parser (the value and flag sets of `crates/cancho/src/vcs_repo.rs:30-110`, `--output`, `--repo`, `--dry-run` on all, "unknown option" and "`--output` is `json`, the only form" as usage errors with the Rust
words), discovery (D2), and the envelope (D4). `cli.cho` gets the routing of D1 in a few lines. The libraries are not rewritten.

**D4. The envelope is written once. [choice]** `{"ok": true, "command": C, …}` and `{"ok": false, "command": C, "refused": {…}}`, pretty, keys sorted, as `jsonwrite.cho` already prints the documents the
libraries answer (`vcs-native.md` §6: byte for byte as `serde_json`); exit 0, 1 for a refusal, 3 for an environment failure.

**D5. Refusals become documents. [choice]** `vcsstorectl` prints `refused TAG`; the Rust command prints the tag, a **message** and the details (a `current` change for `ref-moved`, the candidates for an
ambiguous prefix). The pins hold the messages (`refuse_not_a_repository.json`: ``no `.cancho/vcs` at or above `.` ``), so parity is the Rust sentence, and the compiler in cancho's "the rule's sentence"
decision (`gate.md` G3) does not apply to `vcs`: these are the command's refusals, not the checker's rules. Each slice lists the tags its commands can answer, by reading the `cmd_*` function, and
holds each with a pin or a fixture; **the number of tags is not counted here** (the Rust `vcs` code carries 41 `Refusal::new` sites).

**D6. The oracle is the pins and a committed store. [choice]** `crates/cancho/tests/vcs_repo.rs` builds a repository by running the Rust `record` and compares the commands with the pins. After the Rust code goes there
is no `record` to run. So: a **store committed under `tests/vcs_fixtures/`**, written once by the Rust command with fixed `--time` and `--author` (a store is content-addressed and its documents hold no
clock, so it is reproducible), and a command test (`tests/commands/vcs_repo.sh`, compared with the pins, `<root>` normalised) that runs `init`, `log`, `show`, `status` and `branch` on copies of it. It
needs no Rust binary at test time, which is what makes it a gate stage and not a script run by hand (the fate of `vcsstatus_check.sh`, which is not in `scripts/gate.sh` or CI). The existing
differential scripts stay as the check while the Rust command exists.

**D7. What this does not decide. [choice]** `record` and its gate (the `driver` refactor), `switch`, `restore`, `revert`, `apply` (they need `materialize` and `remove_path`, slice 3b of
`directory-links.md`), `diff`, `blame` (built in R12, §14), `verify` (built in R13, §15), `unlock`, the git bridge (designed in §16); `log --path|--intent|--session|--issue|--author` and `show --patch` (`vcs-native.md` §6 listed them as not done; built in R11, §13); the
crash test; and `canonicalize` (D2).

## 7. R5, `restore`: the design **[read]** unless marked, **[choice]** where it is a decision (2026-11-12; nothing here is built or measured)

What `cmd_restore` does (`crates/cancho/src/vcs_repo.rs:572-604`) **[read]**: refuse `nothing-selected` with no path; resolve `--from` (default `HEAD`) to a change and take its tree; with no `--dry-run` take the **work lock**; scan the working copy; turn each path argument into a repository-relative one (`rel_path`, `vcs_args.rs:116`); for every difference between the working copy and that tree whose path is covered by an argument (`""` covers all, else the path or beneath it), record `{"path", "was": KIND}` and, unless `--dry-run`, `materialize` the tree's entry or `remove_path` the path (what the tree lacks). The answer is `{"from", "restored": [...], "dry_run"}`, `restored` in the order of the diff.

**D8. One module, `vcsrestore.cho`, calling what exists. [choice]** `vcsstatus` already scans and diffs against HEAD's tree (`vcsrepo.emit_files`); `vcsworktree` already writes (27 checks against Rust `restore`). New is the glue: (a) the tree of `--from` instead of HEAD's, (b) the covered-path filter, (c) reading each blob and calling `materialize` with its mode and bytes, `remove_path` for a deletion, (d) the lock. `clivcsrepo` routes `restore` (option `--from`, positional paths, `--dry-run`).

**D9. The work lock. [choice, needs the owner: O5]** Rust writes `PID TIMESTAMP` to `.cancho/vcs/lock` with `O_EXCL` and removes it on drop; a held lock refuses `lock-held` and the document carries `lock`, `pid` and `age_seconds` (the message says to run `cancho vcs unlock`). cancho has no `getpid` builtin: `vcsstore.take_lock` stamps `0 NOW` for refs, which are held for microseconds. For `restore` the lock is held while many files are written, and `unlock` prints the pid. Options: **(a)** stamp `0 NOW` as refs do (a pid of `0` in the stamp, whether the Rust `unlock` accepts it is **not measured**; the pid in `lock-held` is `0`); **(b)** add a `getpid` builtin (touches many pinned counts and needs a reseed: a slice of its own). Recommendation: (a), said in the header, with the document's `pid` as `null` when the stamp holds `0`.

**D10. `rel_path`. [choice]** The Rust function resolves the current directory through links (`canonicalize`), joins, collapses `..` and requires the result to lie under `repo.root` (`path-escapes` otherwise, `path-unsupported` for non-UTF-8). `clivcsrepo` already takes `--repo` as written (D2). The same rule here: join the argument to the current directory as `clivcsrepo.absolute` does and strip the root **as found by upward search**. A difference from Rust arises only when the current directory is reached through a link (the Rust prefix test then sees the physical path, this one the logical one); listed in the header and in a test, not hidden.

**D11. Order and partial failure. [choice]** As Rust: one change at a time in the order of the diff; a failure (`io`, exit 3) stops the command with the files written so far in place (the Rust command does not roll back either, **read**: the loop `?`s out). The temporary file of `materialize` is `NAME.cancho-tmp-0` (`vcs-worktree.md` W3): `status` skips it, so a crash leaves no phantom change.

**What the tests are. [choice, corrected 2026-11-13]** Goldens made by the Rust command on copies of the fixture, for the cases below. **The pins `restore`, `restore_again` and `restore_dry` cannot be used as the design first said:** they come from a repository that has had two `revert`s (their `from` is `935bbc…`), which cancho cannot make yet, so the same cases are made on the fixture instead (the documents have the same shape). The cases: `.` (everything, after the working copy was changed in each way `status` knows: file, mode, link, deleted, a file that became a directory), a path beneath a directory, `--from HEAD~1`, `--dry-run` (nothing written), a name that matches nothing (`restored: []`), no path (`nothing-selected`), a held lock (the fixture with `.cancho/vcs/lock` made; `lock-held` with its `pid` and `age_seconds`), `restore` from a subdirectory (paths relative to it). After each write case the **tree is compared with the Rust command's** entry by entry (`vcsworktree_check.sh`'s comparison), not only the JSON. **Mutants to kill:** the covered-path test dropped (everything is restored), the lock not taken, the order of the diff changed, `--dry-run` writing.

## 8. R6, `switch`: the design **[read]** unless marked, **[choice]** where it is a decision (2026-11-13; nothing here is built or measured)

What `cmd_switch` does (`crates/cancho/src/vcs_repo.rs:532-570`, `move_working_copy` at `:499`) **[read]**, and what the Rust command printed on the fixture **[measured]** (`cancho-darwin` binary, scratch copies of `three_changes`):

* Exactly one positional (`bad-argument`: "`switch` takes one branch or change", for none or two). Unless `--dry-run`, take the **work lock** first.
* The target is: with `--create`, a **new branch at HEAD's change** (`bad-revision` "there is no change to branch from yet" if HEAD has none; `check_ref_name`; `update_ref(heads/NAME, Expect::Absent, ..., "switch --create")` unless dry; a branch that exists is `ref-moved` with `"expected": "absent"`); else, unless `--detach`, an **existing branch** of that name; else `resolve(target)` and **detach** at it (`bad-revision` "names no change, branch or tag").
* If HEAD already is that target, answer `{"command","head","ok","switched": false}` (no `dry_run`, no `branch`, no `discarded` keys), nothing touched. Otherwise diff `HEAD's tree -> target's tree` (`moving`) and `dirty` = the paths `status` lists. A dirty path that is also in `moving` is **in the way**. Blocked = every dirty path (default), only those in the way (`--keep`), none (`--discard`); a non-empty blocked list is `dirty-working-copy` (exit 1) with `"paths"` (sorted). Unless `--dry-run`, for each change in `moving` (path order) `materialize` the new entry or `remove_path`, then **write HEAD** (`ref: refs/heads/NAME\n`, or `ID\n` detached). Answer `{"branch": NAME|null, "command", "discarded": [in-the-way paths with --discard, else []], "dry_run", "head", "ok", "switched": !dry}`.
* **Measured on the fixture:** `--keep` with a dirty file that `moving` does not touch proceeds and carries it (`discarded: []`); `--discard` overwrites only what `moving` names and leaves every other dirty file; `--dry-run` still refuses over a dirty working copy (the check comes before the write); a dry-run switch answers `switched: false` with `dry_run: true`, as it does when HEAD is already there (that one has no `dry_run` key).

**D12. One module, `vcsswitch.cho`, in the shape of `vcsrestore`. [choice]** `switch_command(heap, root, vcs, scratch, target, create, detach, keep, discard, dry, now)`. It reuses `vcsrepo.resolve/tree_id_of/tree_text`, `vcsstore.read_ref/update_ref/take_lock`, `vcsscan.scan`, `vcsworktree.materialize/remove_path`, and the walk of `vcsrestore` for applying a change (the walk `old -> new` is the same merge-walk with `old` the HEAD tree and no filter; `vcsrestore.apply` is made `pub`).

**D13. The dirty set and `in the way` by merge-walks, not a set. [choice]** `dirty` = the paths of the walk `HEAD's tree -> scan` and `moving` = the paths of the walk `HEAD's tree -> target's tree`, both in path order as lines `PATH\n`; `in the way` is their intersection by one merge pass; the refusal lists `dirty` (default) or `in the way` (`--keep`). No quadratic search.

**D14. Writing HEAD. [choice]** `vcsstore.put_whole` (private today, used by `init`) is made `pub` and writes `HEAD` through `HEAD.tmp-0` and a rename: the temporary file is in `.cancho/vcs` (not `.cancho/vcs/tmp` as Rust's `write_atomic`): **a known difference**, invisible to every command (the scan skips `.cancho`). A crash between the working-copy writes and the HEAD write leaves HEAD at the old place with a half-moved tree, exactly as in Rust; `status` shows it.

**D15. The refusal document needs a `paths` member. [choice]** `clivcsrepo` builds `dirty-working-copy` as it builds `lock-held`: tag, message, and the sorted `paths`. A new status code (32 `dirty-working-copy`) in `vcsrestore`'s/`vcsstatus`'s sense is **not** added to the libraries: the command line carries the list in `bytes`, the same way `lock-held` carries the lock text (status 15).

**D16. Order with the lock and the create. [choice]** As Rust: lock, then HEAD's tree, then the create (`update_ref`), then the dirty check. **A difference from Rust that is Rust's:** with `--create` and a dirty tree the branch is made *before* the dirty check could refuse; but `moving` is empty for a create (same change), so nothing can be in the way and the create never refuses for dirt. Kept.

**What the tests are. [choice]** Goldens by the Rust command on copies of the fixture; after each write case the **working copy and HEAD file are compared with the Rust command's**. Cases: `switch main` (no-op), `--create topic` (HEAD file, ref file), `--create` twice (`ref-moved`), `--create` bad name, `--create` in an empty repository (`bad-revision`), a branch at `HEAD~1` then switch to it (files change, HEAD is the branch), switch back, `--detach main`, `HEAD~1` (detached, `branch: null`), a change id, `nosuch`, no argument, two arguments, a dirty file blocking (default, with `paths`), the same with `--keep` where the dirty file is in the way (blocked) and where it is not (carried), `--discard` where it is in the way (`discarded`), `--dry-run` (nothing written, HEAD unchanged), an added and a removed file and a mode change between the two changes, from a subdirectory, the lock held (`lock-held`) and `--dry-run` with the lock held. **Mutants to kill:** HEAD not written, the dirty check dropped, `--keep` treated as `--discard`, `--dry-run` writing, the lock not taken, the in-the-way intersection returning everything dirty.

**Not in R6:** `revert`, `apply`, `record`'s deletions, `merge`; a switch of many thousands of files; a crash between the writes and the HEAD write.

## 9. R7, `apply` (and `unlock`): the design **[measured]** against the Rust command unless marked **[choice]** (2026-11-13; built and measured at the end of this section)

**Why not `revert`.** `revert` ends in `commit_tree` (the gate, the intent, the new tree and change object): that is `record`, which has no native form yet, so `revert` waits for it. `apply FILE` and `unlock` need only
the lock, the working copy and one JSON file. The Rust command was run on a scratch repository for each line below.

* **E1. The file.** One positional, else `bad-argument` ``"`apply` takes a JSON file of edits"``. It is read from the **current directory**, not the repository root; unreadable: tag `io-error`, exit 3, ``cannot read FILE: ...``.
  A JSON array of objects with `path`, `old`, `new`, all strings; **extra keys are ignored**; anything else is `bad-argument` (exit 1) with the parser's sentence, which is serde's (`missing field \`new\` at line 1 column 27`).
  **[choice]** the tag and exit are the Rust command's, the sentence is `FILE: ` and the parser's own words; the golden test compares tag and exit for these, as D5 does.
* **E2. Paths.** Each `path` goes through `rel_path` (the cwd, `..` collapsed, outside the root is `path-escapes` with ``\`../x\` is outside the repository``), as `restore` does; the helper of `restore_in` is shared, not copied.
* **E3. Order and atomicity.** Edits are grouped by path, **paths sorted by bytes**, each path's edits in file order; the work lock is taken **before the file is read and also under `--dry-run`** (`restore` and
  `switch` do not take it when dry); every file is read and edited in memory before any is written, so a refusal in the second path leaves the first untouched (measured: `e.sh` is refused before `o.txt` is looked at).
  An empty list is `applied: []`, ok, with the lock taken.
* **E4. The anchor.** `old` empty: `anchor-not-found` ``an empty anchor in \`P\```. Otherwise `old` must occur **exactly once, counting non-overlapping matches from the left**: `aa` in `aaa` occurs once (measured: the file became
  `ba`), not twice, so it is *applied*. Not found: `anchor-not-found` ``the old text of an edit is not in \`P\```; two: `anchor-ambiguous` ``... occurs more than once in \`P\```. Edits of one path apply in order, each to the text the last one left.
* **E5. Reading and writing.** The file is read whole as UTF-8 (a missing one, a directory: `io-error`, exit 3, ``cannot read P: ...``). The Rust write is **in place** (`fs::write`, then the old permissions set again) and **follows a link**: through
  `l -> o.txt` it changes `o.txt` and leaves the link (measured). **[choice]** cancho writes with `vcsworktree.materialize` (a temporary file beside it, renamed over: whole or old), mode `0644`/`0755` from the owner's execute bit,
  and **refuses a link** with `io-error`. **Known differences, to be listed in the header:** a link; a mode other than those two (`0600` becomes `0644`); a file that is not valid UTF-8 is refused where Rust also refuses it (same).
* **E6. The document.** `{"applied": [paths sorted], "command": "apply", "dry_run": B, "ok": true}`; `--dry-run` writes nothing.
* **`unlock`, E7.** Lists `refs/**` for names `lock` or ending `.lock`, then the store's top `lock`, reads each as `PID SINCE`, removes it unless `--dry-run`; the document is
  `{"command","dry_run","ok","removed":[{"age_seconds","lock","pid"}]}`, `age_seconds` = now − SINCE (at least 0), `pid` and `age_seconds` null when the text does not parse. The pin has `removed: []`. **[choice]** order: sorted by path
  (Rust's is the directory's, unspecified), the top lock last as in Rust; a lock cancho made says `pid` 0 (D9).
* **Where.** A new `vcsapply.cho` (the anchor, the grouping, the document: pure, testable without a repository), the command in `clivcsrepo.cho` (the options, the file, `rel_path`, the lock), routed like `switch`.
  Tests: pins `apply`, `refuse_anchor_not_found`, `unlock`; goldens of the Rust command for E1–E6 on a copy of the fixture; mutants: the overlap rule (`aa`/`aaa`), the order of paths, the lock under `--dry-run`, the
  empty-anchor test, atomicity (a second file's refusal after a first one's success).

**R7, built and measured (2026-11-13, Darwin, macOS 26.2, Apple silicon; `main` at 90d7cfab).** `cancho vcs apply FILE` is `vcsapply.cho`'s (E1–E6) and `cancho vcs unlock` is `vcsunlock.cho`'s (E7); `clivcsrepo.cho` reads the file from the current directory,
and `cancho.files` gained the two modules and nothing else. **The chain built from the compiler of R6 reproduces itself** (stage 2 = stage 3). `tests/commands/vcs_repo.sh` goes from 200 to **325 checks**, the 200 unchanged: 27 `apply`
documents and the working copy each leaves (`apply_*.json` and `.tree`, from the Rust command: two edits of one file, two files in both orders, the overlap rule, `--dry-run`, a refusal in the second file or in the first, no anchor, two,
an empty one, `..`, an empty list, the execute bit, escapes and a non-BMP character, `./sub/../notes.md` as a spelling, two spellings of one file, a subdirectory, CRLF, a deletion, 5,000 lines, spaced JSON, an extra key), 9 refusals checked by tag and exit
(a file that is not there, a directory, the root, an empty path, an object, a missing `new`, a number as `old`, truncated JSON, a trailing comma), the held lock under `--dry-run`, and 13 `unlock` documents with the locks each leaves.
**Found by the differential run before the tests were written, not by a review:** (1) the first build trapped (`Illegal instruction`) on any file with two edits and left its lock: `vcsscan.sorted` is for tree lines and compares from byte 72,
so `vcsapply` sorts its own paths; (2) **a bug in R5 and R6, not in the Rust command: `walk.collapse` collapses `a/..` but leaves `.` components, so `restore ./notes.md` answered `ok` with `restored: []` and changed nothing** (measured with the R6
build: the file kept its scribble). `vcsapply.relative`, now the one path helper of `apply` and `restore`, drops them; two checks pin it. (3) The Rust anchor message names the path as the edit spelled it (`./sub/../notes.md`), not the normal one; so does this.
**Mutants, each killed by `vcs_repo.sh`:** the overlap rule (`aa` in `aaa` read as twice: 2 checks fail), the order of paths (descending: 8; the sort that keeps only the first: 4), the lock under `--dry-run` (2), the empty-anchor test (1),
checking and writing in one pass (18), `unlock --dry-run` that removes (1), the `.` components kept (6). **Known differences:** the file is replaced through a temporary beside it (E5: a link is refused, `0600` becomes `0644`, a path under `.cancho` is refused with
`path-unsupported`); the messages of `bad-argument` and `io-error` (tag and exit are equal, and those cases are checked by tag and exit); `unlock` lists sorted by name, Rust in the directory's order (two locks in `refs/heads` came out in the other order on this
volume). **Not covered:** `revert` (needs a native `record`), a crash between two files' writes, duplicate keys in an edit (the first wins here; serde's last), an edits file with a byte-order mark, a lock directory entry that is a link, Linux (CI).

## 10. R8, `record`: the design **[read]** from `vcs_record.rs`, **[measured]** where it says so (2026-11-14; the Rust command was run on a scratch repository; nothing here is built yet)

**Why `record` next.** `revert` ends in `commit_tree` (§9), and `commit_tree` is `record`: the gate, the lock, the tree and change objects, the branch move. So `record` is built to be shared (`commit_tree`'s
shape), `revert` is the slice after it. (This sentence first said "and `tag` after that"; the Rust `cancho vcs` has no `tag` command and `vcs-cli.md` lists it as not built, so the slice after `revert` is `diff`, §12. Corrected 2026-11-14.) Most of the parts exist in cancho already: the scan (`vcsscan`), the tree diff and `covers` (`vcsrestore`), blobs (`vcsstore.put`), the line diff and anchored
edits (`vcsdiff`, a port of `diff_text.rs` and `anchor.rs`), the change encoder (`vcschange`), `update_ref`, the work lock (`take_lock`), and the compiler's own entry points in `driver.cho`.

* **G1. Arguments.** Paths, or `--all`; neither: `nothing-selected` (``"name the paths to record, or pass --all"``, exit 1, measured). Each path through `vcsapply.relative` (the helper `apply` and `restore` share).
  Options: `--author`, `--time` (unix seconds, else `bad-argument`), `--intent-prompt` with `--intent-model`, `--intent-session`, `--intent-issue` (the last three only with a prompt), `--expect REV`, `--no-gate`,
  `--dry-run`. `CANCHO_AUTHOR` and the default `cancho <cancho@localhost>` as in Rust.
* **G2. The new tree.** HEAD's tree with each difference between it and the scan applied that the selection covers (`vcsrestore.covers`); `touched` is those paths in the diff's order. An unchanged tree is `unchanged: true`
  and the HEAD change (the empty repository: `nothing-to-record`); the document then repeats that change's tree, parents, decls and intent (measured).
* **G3. The gate.** Each touched `.cho` file still in the new tree is checked as the program it belongs to: itself, the files of the tree that declare the modules it imports (transitively), and the standard
  library when something imports `std`. **Measured, and decisive:** `cancho check` on a library file is refused (`no main function`), so the command is not what the gate runs; `driver.run_many` **mode 10**
  (`check_quiet`) is the check "as the build checks it, with no `main` asked for", which is the Rust gate's own scope (`check_candidate` does no `main` check). The first refusal is `gate-failed`, with `path`, `rule`, and
  `diagnostics` (measured: `a.cho: type-mismatch: expected `int`, found `bool``). **[choice]** the rule tag and path are the Rust command's; the *message* is the native checker's own words, so the golden test compares
  tag, rule and exit for this refusal, as D5 does. `gate: {ran, checked}` lists the files checked in the order of `touched`; the attestation is `gate:cancho-check:ok:N`; `--no-gate` checks nothing and attests nothing.
* **G4. Declarations and edits.** For each difference: a `.cho` file that parses has a declaration view (name `fn module.name` or `type Name`, signature and body ids), and the change lists `added`, `signature-changed`,
  `body-changed`, `removed`, sorted by name; any other text file that is valid UTF-8 on both sides gets the anchored edits of `derive_edits`. Natively the ids are `driver` mode 14 (`identity.pairs`), run on the one file.
  **Read in `identity.cho` after the first draft of this section, and a correction to it:** mode 14 (`pairs`) has no names; mode 15 (`published`) has `module NUL name NUL sig NUL body NUL labels` for each function and
  static, which is what `fn module.name` needs. **No mode lists the types:** `type Name` lines exist only in `ids`' printer (mode 9, which writes to the output, not to a buffer). So G4 needs one new native function,
  `identity.type_lines` (the printer's type lines into a buffer) and a mode for it, which is new code in `identity.cho` and the driver, not a reuse. **Built and measured (2026-11-14):** `identity.declared` and driver mode 20 write `kind NUL module NUL name NUL sig NUL body` for each type, function, foreign function and static. On a file with two types and two
  functions in a module, its 8 ids equal the 8 that the Rust `cancho ids` prints (checked by eye, hash by hash), and the keys it gives, `fn lib.a.f` and `type E`, are the names of the Rust record's decls. **Not
  measured:** statics (the Rust `cancho_id` lists them with the functions, and so does mode 20, but no sample was run), and a file with the same type name in two modules (Rust's map keeps the last).
* **G5. The change object, byte for byte.** The id of a change is the hash of its encoding, so **the oracle is exact**: the same repository state with `--time` and `--author` fixed must give the same `change` and
  `tree` ids as the Rust command (measured here: `94c4bb5e…` for the scratch repository of the test). `tz` is `+0000`. Any difference in a decl, an edit or the attestation shows as a different id, which is why this
  slice can be tested by comparison rather than by reading.
* **G6. Storing.** Not under `--dry-run`: take the work lock, read HEAD again under it and refuse `ref-moved` (with `current`) if it moved; write the blobs not yet stored, the tree, the change; then move the branch
  with `update_ref` (expect: `--expect`, else HEAD's change, else absent; note `record`), or set a detached HEAD. `lock-held` as for `apply`. The lock is not taken for `--dry-run`.
* **G7. The document.** `branch` (null when detached), `change`, `command`, `decls`, `dry_run`, `edits` (the count), `gate`, `intent`, `ok`, `parents`, `recorded` (fresh and not dry), `touched`, `tree`, `unchanged`
  (keys sorted, as the envelope does).
* **G8. Where.** A new `vcsrecord.cho` (selection, the new tree, the gate's program assembly, decls, the change), the command in `clivcsrepo.cho`, routed like `apply`. **A risk, said now:** the module imports
  `driver.cho`, the compiler's entry; it is in the standalone binary already, but the *seed* knows only what the seed knows, so the first thing to check is that a program importing `vcsrecord` builds from the
  committed seed (R0 had this problem with `dir_readlink`).
* **Tests.** Goldens made by the Rust command with `make.sh` for: the empty repository, the first record, again (`unchanged`), `--dry-run`, a selection of one path, a deletion, a mode change, a link, a text edit
  (`edits`), a `.cho` change of each decl kind, a gate refusal, `--no-gate`, `nothing-selected`, `--expect` wrong (`ref-moved`), a bad `--time`, `--intent-*`, a detached HEAD, `lock-held`. Each also checks the
  working copy's store: the change loads, the tree lists, the branch is moved, the lock is gone. Mutants: the covers test, the order of `touched`, the gate on a file the change deletes, the HEAD re-read under the lock, the
  `unchanged` branch, the attestation text.

**R8, built and measured (2026-11-14, Darwin, macOS 26.2, Apple silicon).** `record` is `vcsrecord.cho` (new tree, gate, change, store, document), `vcsdecl.cho` (the declaration view and its changes, the anchored edits) and the command in `clivcsrepo.cho`
(routed like `apply`; `--all`, `--no-gate`, `--author`, `--time`, `--intent-*`, `--expect`, `--dry-run`). New in the compiler's own modules: `identity.declared` and driver mode 20 (G4), `vcsworktree.link_under`, and `vcsstatus.head_info`
and `vcsrepo`'s three `emit_*` made `pub`. **The oracle held:** with `--time` and `--author` fixed, the document, the change id, the tree id and the whole store (every object name and ref, by checksum) of the native command equal

## 12. R10, `diff`: built and measured against the Rust command (2026-11-14, Darwin, macOS 26.2, Apple silicon)

**What `tag` was.** The order given was `record`, `revert`, `tag`. The Rust `cancho vcs` has no `tag` command (`vcs_repo.rs` dispatches `init status diff record revert log show blame branch switch restore verify unlock apply import-git export-git`;
`vcs-cli.md` lists `tag` as not built), so there was nothing to route and no oracle to measure against; §10's "and `tag` after that" is corrected there. The next command with an oracle that is not native is `diff`.

**The design is the Rust command's** (`cmd_diff`, `diff_files`, `unified`): `diff [REV [REV]] [PATH...] [--context N]`. The first two words that resolve to a change and are *not* a file or directory in the current directory are the
revisions (a third resolvable word, or one that names a file, is a path); the rest are paths (`path-escapes` outside the repository). No revision compares HEAD's tree with the working copy, one compares that change's tree with it, two compare
the two trees. The document is `{"command", "files", "from", "ok", "to"}` (`from` and `to` are the resolved ids, or `HEAD` and `working copy`); each file is `{"binary", "decls"?, "hunks"?, "mode"?, "path", "status"}` with `status`

§10); `hunks` for a text file whose status is not `mode`, unified, `--context` lines (default 3) around each change, hunks whose context touches joined. A blob the store does not have is read from the working copy (a link's blob is its target).

**Built.** `vcsdiffdoc.cho` (519 lines: the unified hunks over `vcsdiff.diff_lines`, the walk of the two trees, the entries' texts, the document), `diff` in `clivcsrepo.cho` (the words, `--context`, the revision-or-path rule with

directory): stdout, stderr and exit status equal in all. `tests/commands/vcs_repo.sh` goes from 516 to **572 checks** with 56 more goldens made by the Rust command (`make.sh`): clean, one and two revisions, both orders, paths and
directories, `.`, three values of `--context` (and the exact gap of `2 × context` that joins two hunks, and one more that does not), modified, no newline at the end, Unicode, added (empty, exec, binary, not UTF-8, in new directories),
deleted, mode, mode and text, links (added, changed, to and from a file), `main` against `wide`, `.cho` bodies, signatures, additions, removals, deletions and an unparsable side, a bad or negative or valueless `--context`, a path outside, a name
nothing has, a file or a directory named like a branch, a third revision as a path, an unknown option, no repository, and from a subdirectory (three forms). **Mutants, all killed (16):** the join of hunks that touch, the new start with a

revision-or-path word is "a directory, or a file that can be read" (Rust: `Path::exists`), so a file that exists and cannot be read is taken as a revision when one resolves; the `declared` view of §10's known difference applies.
**Not covered:** a file of over 200,000 lines (one replacement, as `diff_text.rs`; unit-tested in Rust, not here), a working copy changing while it is read, Linux (CI).

## 13. R11, `log` filters and `show --patch`: built and measured against the Rust command (2026-11-14, Darwin, macOS 26.2, Apple silicon)

## 14. R12, `blame`: built and measured against the Rust command (2026-11-15, Darwin, macOS 26.2, Apple silicon)

**The design is the Rust command's** (`cmd_blame`, `blame_decl`). `blame PATH [--rev REV] [--decl NAME]`, one path (else `bad-argument`, "`blame` takes one path"), relative to the current directory and inside the repository
(`path-escapes`). Lines: the walk is down the first parents from REV (HEAD by default). Each version's lines are compared with the next older version's by the line diff (`diff_lines`, the histogram diff of `diff`), a line the diff says the newer
version *added* belongs to the newer change, and the rest carry on; what reaches a version with no parent, or a parent without the file, belongs to that version. The document is `{command, lines, ok, path, rev}`, each line
`{author, change, intent, line, subject, text, time}` (`intent` is `null` without one; `text` has its `\n` taken off). A file that is not UTF-8 (a NUL is fine) is `binary-file`, in REV or in any older version the walk reaches; a path that is not a
file in REV (a directory too) is `path-not-found` ("`P` is not in" and the first 12 digits of the change). `--decl NAME` gives, instead, the oldest change on the first-parent chain in which the declaration `NAME` (a key of the declaration view of §10,
`fn a.twice`, `type T`) has the same signature and body as at REV: the change as `log` lists it (with `parents` and `tz`) plus `decl` and `path`; a name the file does not have is `decl-not-found` with the file's names in `declarations`, a file that
does not parse is `binary-file` ("does not parse as cancho"); in that walk a version whose blob cannot be read or is not text or does not parse ends the walk.

**Built.** `vcsblame.cho` (about 650 lines: the walk with the line map, the rows, the declaration walk, the refusal documents), `blame` in `clivcsrepo.cho` (`blame_in`; the file is 1,853 lines), `--rev` and `--decl` in `clivcsopts.cho`, and

`vcsblame.cho`. The chain built from the previous compiler reproduces itself (stage 2 = stage 3), no reseed. **Measured:** 38 scripted cases, then three repositories of 18 randomized edits each (inserts, deletes and changes of a 20-line file,
function bodies changing, a file removed and back, CRLF) blamed at every revision, as text and for each of four declarations: **345** more, then 12 more (a subdirectory, an empty file, an unparsable `.cho`, a 3,000-line file in 0.19 s against the Rust
command's 0.05): stdout, stderr and exit status equal in all 395. `vcs_repo.sh` goes from 612 to **658 checks** with 46 more goldens made by the Rust command (the command's every refusal, the three-version case where a hunk replaces two lines by one,
which only a fourth version can show, the default revision on another branch, a parent that is binary under a text file, one declaration and none in the list). **Mutants:** 18; 16 killed, one equivalent (not giving what is left to a parentless version
changes nothing once the loop ends because none is left), and one **not covered**, the leniency of the declaration walk toward a blob the store cannot give (needs a store with a missing blob; the lines walk refuses there, the declaration walk stops).

**Known differences:** the declaration view's (§10: two modules declaring the same type name); the `\u` escapes a change written by something other than the Rust command might use are read by both. **Not covered:** a merge change's second parent

## 15. R13, `verify`: built and measured against the Rust command (2026-11-15, Darwin, macOS 26.2, Apple silicon)

**The design is the Rust command's** (`cmd_verify`). Every object of the store, kind by kind (`blob`, `tree`, `change`) and by id in order, is read and checked: its name is an id (else `object-corrupt`, "KIND NAME: not an object name"), the store reads it
(`object-missing`, `object-corrupt` when it does not hash to its name, `io-error`), a tree decodes and the store has each blob it names ("blob B (in tree T, PATH)"), a change loads (the types of `Change`, a tree and at most two parents that are ids)
and the store has its tree and each parent. Then every ref under `heads`, `tags` and `remotes` ("change C (ref heads/x)") and HEAD ("change C (HEAD)") must name a change it has. All sound: `{command, locks, objects, ok, refs, sound, tmp_garbage}` (`locks` as
`unlock` lists them, not removed; `tmp_garbage` the entries of `tmp/`); else a refusal carrying `problems` (`{object, tag}`), `objects` and the tag of the first problem (`object-missing` or else `object-corrupt`), exit 1. A ref or HEAD that holds no id
is refused at once, with that sentence and without the list (Rust returns the error).

**What it took.** Two of the Rust decoders are not the strict readers the native commands have, and `verify` is where the difference shows: `Tree::decode` accepts a tree that is unsorted, has `\r\n` endings or no newline at the end (it reads `lines()`,
sorts, then checks paths, duplicates and a path that is the directory of the next), and `Change::load` is `serde`: every optional part must be of its type (`intent` an object with a `prompt`, `decls` and `edits` lists of objects of strings, `attestations`
strings, `git` with `Bytes`, which may be `{"hex": ...}` read by `from_str_radix` so that a `+` can begin a pair), and a field it names may not be there twice. `vcsverify.canonical_tree` and `vcschange.well_typed` are those rules.
`vcsunlock.lock_items` was split out of `unlock_command` (the locks, each removed or not); `vcsstore.read_ref` and `list_refs` now say which ref held no id (so the refusal can name it); `status 50` (a complete refusal document, exit 1) is `blame`'s.

**Built.** `vcsverify.cho` (about 640 lines), `verify_in` in `clivcsrepo.cho` (1,877 lines), `cancho.files` gained `vcsverify.cho`. The chain reproduces itself (stage 2 = stage 3), no reseed. **Measured:** 38 scripted corruptions of a three-object store
(damaged, empty, missing and stray objects of each kind, refs and tags and remotes to nothing, nested refs, bad and detached and unborn HEAD, locks, `tmp` files, a damaged file that cannot be read, several problems at once, no `objects`, `refs` or `tmp`)
and 68 crafted objects (a true hash over a tree or change the Rust decoder reads or refuses: unsorted, CRLF, blank line, duplicate, directory and file, a path with a dot or a quote, a bad mode; a change with each optional part wrong or right, hex `+f` and `abc`
and `0g`, a float time, a time beyond 64 bits, trailing text, a duplicate field): stdout, stderr and exit status equal in all but one (below). `vcs_repo.sh` goes from 658 to **742 checks** with 77 more goldens made by the Rust command (the crafted objects are
committed under `tests/vcs_fixtures/verify_objects/`, each one file, since the hasher that made them is not part of the repository), and checks that `verify` leaves the locks it lists and exits 0 or 1. **Mutants:** 15 and four more of the ones the first
run let live; all killed but one that cannot be reached (`has_object` refusing a name that is not an id: every caller has checked it). Four survived the first run and three got a case (the order of the kinds needs a tree and a change that are both wrong, a
CRLF only shows in a missing blob's path, an empty tree). **Known differences:** the shared JSON reader (`jsonread`) refuses any key written twice, `serde` only the ones `Change` names, so a change with an unknown field twice is refused here and sound
there; the ids of a kind are sorted by directory, then name (the same as sorted whole when every directory name has two characters, as the store's do); locks come sorted (R7); a directory that is a link is not entered. **Not covered:** a store too large for
the memory it is given (every object is read whole, as Rust does), Linux (CI), a tree with a path that is not UTF-8 (the Rust decoder refuses it with the whole tree; mine does too: compared by hand, not in the goldens).

## 16. R14 to R16, the git bridge: the design **[read]** from `bridge.rs` and `gitread.rs`, **[measured]** where it says so (2026-11-15; nothing here is built)

**What the Rust command does** (`import_git`, `export_git`, `GitRepo`; about 1,500 lines with `inflate.rs` and `sha1.rs`). *Reading:* a git repository's objects from loose files, from pack files (index version 2: fan-out table, sorted ids, offsets; objects of type 1 to 4, `ofs-delta`
6 and `ref-delta` 7, a delta chain applied from its base, at most 5,000 deep), and from the object directories `info/alternates` names (at most 8); refs from `packed-refs` and the loose files under `refs/heads`, `refs/tags` and `refs/remotes`; HEAD as a branch name or an id. The object ids are
trusted, not recomputed. *Import:* every commit reachable from a ref or HEAD (annotated tags peeled, at most 8 deep), parents before children; each tree flattened to `(path, mode, blob)` (a submodule is `submodule-unsupported`, a mode other than `100644`, `100755`, `120000` and the directory is
`mode-unsupported`, a name that is not UTF-8 is `path-unsupported`); each blob put in the store; one change per commit: the tree, the parents in order, author, time and zone read from the `author` header, the commit message as the `intent` prompt (trailing whitespace trimmed), and `git`, the header lines after the last
`parent` and the message **byte for byte** (a `Bytes`: text, or `{"hex": ...}` when not UTF-8). Each is **self-checked** (the commit rendered back must hash to the id it came from). `.cancho/vcs/gitmap` (`GITID CHANGEID` lines, sorted, written every 200 commits and at the end) makes a second import skip what is there. Refs: `refs/heads/B` becomes
`heads/B`, `tags/T`, `remotes/R` (a ref that exists and differs is kept and reported, `refs_kept`); HEAD follows git's when this repository has no change; the files of HEAD's tree are written to the working copy unless `--no-checkout` or it is not clean. A repository that does not exist is made (not with `--dry-run`, which refuses
`not-a-repository`). *Export:* every change reachable from a ref (and HEAD) in parents-first order; each tree nested again with git's order (a directory sorts as `name/`; mode `40000`); each object written as a loose file (a zlib stream of **stored blocks**) unless it is there; the commit is `tree`, `parent`s, then the stored headers and message, or, for a change made here, an
`author`/`committer` and a message of the prompt and trailers (`Cancho-Change`, `Cancho-Intent`, `Cancho-Session`, `Cancho-Model`, `Cancho-Issue`); refs and HEAD written; every imported commit compared with the id it came from.

**Measured today** (the Rust command, release build, macOS arm64, 2026-11-15; `git` used only to measure, as in `vcs-cli.md` R6). *The repositories* have grown since R1 and are no longer loose: `cancho` has 1,659 commits reachable (209 merges), 37,247 objects (23 packs holding 33,705 of them, 54.8 MiB, the largest 18.5 MiB, and 7,674 loose); `cancho-forge` 233 commits (72 merges), 5,139
objects (one 1.7 MiB pack with 1,196, the rest loose). In the packs: `cancho` 16,269 `ofs-delta` and **2,406 `ref-delta`**, the deepest chain 42; `cancho-forge` 848 `ofs-delta`, none `ref-delta`, deepest 24. So `ref-delta`, whose base is found by id among the packs and the loose files, is needed, and a chain is deep enough that its application must not recurse without bound. Over all their objects the
modes are `100644`, `100755` and `40000` only (no link, no submodule, no other mode), no tree name and no commit is not UTF-8, the only header after `committer` is `gpgsig` (960 and 111 commits; multi-line, the continuation lines begin with a space), the largest object is 2.8 MB (`MAX_BLOB` is 16 MiB). **So the real histories never exercise the link mode, the refusals, the hex form of `Bytes`, an annotated
tag, `packed-refs` or an alternate; those need fixtures made for the purpose.** *The round trip:* `cancho-forge` imported in 10.1 s (1,128 new blobs, 49 branches, 63 remote-tracking refs, **0 self-check mismatches**), exported in 1.0 s; the 233 commits `git rev-list --all` gives are the same 233 in the export, `git fsck --strict` passes, and every ref has the same id but one: `refs/remotes/origin/HEAD`, a symbolic ref, which is not imported (as `vcs-cli.md` R1 says). `cancho`'s `--dry-run`, which reads, flattens, hashes and self-checks everything and writes nothing: **4.0 s** for the 1,659 commits, 0 mismatches. So of the 94 s `vcs-cli.md` R1 measured for the whole import, about 4 s is reading;
the rest is writing 826.9 MiB of objects. *What the native side has:* `sha1.cho` (240 MB/s in memory, `vcs-native.md` §2); `std.flate` with `unzlib` (the Adler-32 checked; I read a 7.2 MB stream into 25.3 MB in 0.18 s of CPU, 140 MB/s of output including the read, and a stream cut at 100,000 bytes answers status 2) and `zlib` (compressing); `file_pread`; and a read of a 25 MB input into one buffer works (the `sha1sum` program,
equal to `shasum`). It has no pack reading, no delta, no git tree or commit reader, no `gitmap`, and `vcschange` does not write the `git` member. *The durability of the store differs:* on this machine `fsync` takes **58 µs** a file and `fcntl(F_FULLFSYNC)` **4,570 µs** (300 files each). Rust's `File::sync_all` is the second on macOS (as its documentation says; I did not read its source here); the native `file_sync` is `fsync(2)` (`file-writes.md`). Recording 1,500 small files takes **0.31 s** natively (0.2 ms a file) and **8.8 s** with the Rust command (5.9 ms a file, and each file there is a blob, a tree entry and a write of a ref's log): a gap of the size of the two sync calls, not proved to be them. If it is them, the native store as built is not as durable as the Rust one against a power cut on a Mac (not against a crash of the process).
Whether that is intended was not decided anywhere I can find (decision 1).

**The plan: three slices, each measured against the Rust command on both histories and on fixtures, each ending in a pull request.**

* **R14, the reading side: `import-git --dry-run`.** `gitread.cho` (loose objects, pack index v2, pack entries, delta application iterative, `ref-delta` by lookup across packs and loose files, alternates, `packed-refs`, refs, HEAD), `gitparse.cho` (commit, tree and tag parsing; the flattening; `author_fields`), `vcschange` writing the `git` member with `Bytes`, the self-check
(`commit_bytes`, which R16 reuses), and the command's arguments. It writes nothing and refuses `not-a-repository` as Rust does. *Done when:* (1) **every object of both repositories read natively hashes to its own name** (loose, packed, deltified; this oracle needs no other implementation); (2) the dry-run document is equal to the Rust one (`commits`, `already_imported`, `self_check_mismatches`, the refusals) on both histories and on the fixtures; (3) mutation tested; (4) the gate, `fmt`, `clippy`, `cargo test`.

**Decisions for the owner. [choice]**
1. **Durability of the native store.** Match the Rust command on macOS (`F_FULLFSYNC`, which would put the native import of `cancho` near the 94 s of the Rust one, which is mostly this) or keep `fsync(2)` (which a power cut can lose on a Mac; a process crash cannot). *Recommended:* keep the native store's policy for these slices, say it in §16 and in `vcs-native.md`, and settle the full sync as its own change to `file_sync` (it touches every native write, not only the bridge); the import is restartable either way (`gitmap` is written every 200 commits, objects are content addressed).
2. **Export compression.** Stored blocks (what Rust does; the object files compare byte for byte) or `std.flate.zlib` (smaller files, by an amount not measured here; the ids are the same). *Recommended:* stored blocks now, compression as an option after R16 if size matters.
3. **`git` as a measuring tool.** Fixtures and the oracle runs use the `git` binary (`fsck`, `rev-list`, `for-each-ref`, `pack-objects`); the commands never do, and the gate does not (the fixtures are committed). Same rule as R6. *Recommended:* yes.

**Decided (2026-11-16, the owner: "go with the recommendations").** 1: keep the native store's `fsync(2)` policy; the full sync is its own later change to `file_sync`. 2: stored blocks. 3: `git` is a measuring tool only.

## 18. R15, `import-git` (writing): built and measured against the Rust command (2026-11-16, Darwin, macOS 26.2, Apple silicon)

**What R14 left, and what R15 adds.** R14 reads, flattens, checks and self-checks; it builds each change in memory (`vcsgit.rendered`) and writes nothing. R15 is the same walk with the writes the Rust `import_git` does after the check, in the Rust order: for each commit not in the `gitmap` (or whose change the store lacks): blobs (`store.put`, `new_blobs` counts those the store did not have), the tree object, the change object (JSON, with the `git` member), the self-check, the `gitmap` entry, the `gitmap` file rewritten every 200 new commits and at the end; then the refs (`heads/`, `tags/`, `remotes/`; a ref that exists and differs is kept and reported in `refs_kept`, a name `check_ref_name` refuses is reported there too), HEAD (follows git's when the repository has no change yet and the branch now exists), and the checkout (HEAD's tree written to the working copy unless `--no-checkout`, or the working copy is not clean, or there is no change). ## 19. R16, `export-git`: built and measured against the Rust command (2026-11-16, Darwin, macOS 26.2, Apple silicon)

**What the Rust command does** (`export_git`, `Exporter`, `commit_bytes`, `native_message` of `bridge.rs`; read, and each claim below was then run). The tips are the refs of `heads`, `tags` and `remotes` in that order (each sorted by the bytes of its names), then HEAD's change when no ref holds it. The changes reachable from the tips are visited with a stack, parents first and the first parent first, each only once (`seen` is the set of changes popped, not pushed). Each change's tree is exported once (by tree id): every subtree is a git tree object (`mode name\0 id`, a directory as `40000`, in git's order), each blob is read from the store once and written once. The commit is `tree`, the `parent`s, then, for a change that came from git, the stored header lines, an empty line and the stored message; for a change made here `author WHO` and `committer WHO` (`AUTHOR TIME TZ`), an empty line, the prompt with its trailing white space cut, and the trailers `Cancho-Change: ID`, `Cancho-Intent: recorded` (only when there is an intent), `Cancho-Session`, `Cancho-Model` and `Cancho-Issue` (each only when the intent has it). An object is a loose file `objects/XX/REST` holding a zlib stream of **stored blocks**, left alone when it is there; refs are `refs/NAME` with the git name and a newline; HEAD is `ref: refs/heads/B` or a git name. The directory is made with `objects/tmp`, `refs/heads` and `refs/tags`, and a `config` of a bare repository unless there is one. Every commit that came from an import (a line of the `gitmap`) is compared with the name it had. **A thing the source did not say until a run did:** with `--dry-run` the trees are not exported and each commit is hashed with a tree of 20 zero bytes, so *every* imported commit shows up as a mismatch in a dry run (`equal` is 0). The command in cancho does the same, and `dry_plain.json` pins it.

**Where the code is.** `gitout.cho` (pure: the stored-block zlib stream with the Adler-32, the loose object, the name of an object, the head and the two forms of a commit, the message of a change made here; 7 tests), `gitidtab.cho` (pure: a table from the first 160 bits of an id to a tag, a number and a 20-byte git name, so that no buffer of ids sits beside a table; 2 tests), `vcsgitout.cho` (the export: tips, the order, the nested trees, the objects, refs, HEAD, the comparison and the document), `vcschange.cho` (the readers of the text of a change: the decoded author, zone, intent parts and the two `Bytes` of the `git` member, a string or the bytes of a `hex`), `clivcsgit.cho` (the arguments of `import-git` and `export-git`, moved out of `clivcsrepo.cho`, which went from 1,937 lines to 1,836; `flagged` moved to `clivcsout.cho`) and the routing in `clivcsrepo.cho` (command 15). `vcsstore.walk` is `pub` (a directory made below another). No Rust, no Python, and no `git` in the command.

**How it works without keeping the history in memory.** One pass finds the order (the DFS above, each change loaded to read its parents; the stack and the order are int slices sized by the number of change objects the store has, counted by listing `objects/change`), a second goes through the order: the commit's tree is exported when its tree id has not been (`gitidtab`, keyed by the store's tree id), the commit written, and its git name put in the table of changes, where the next commit finds its parents. A blob's git name is in a table keyed by the store's blob id (sized by the number of blob objects), so a blob is read once. A tree's lines are nested without a sort: the store's tree text is in the byte order of the flat paths, and that order *is* git's (a directory sorts as `name/`, and `.` and `-` sort below `/` and the digits above, in both), which `vcsobj.tree_status` checks (strictly increasing paths) before the export uses it; the Rust command sorts the rows anyway. Memory is a few int slices and the one tree being written: **42 MB** for `cancho`.

**Measured** (the Rust command as oracle, `git` only to measure). *The git directories are equal:* for the 17 repositories of `tests/vcs_fixtures/git/` whose import the Rust command takes (the others import nothing, so there is nothing to export; `odd` has its octopus branch taken out first, as the Rust command refuses a change of three parents on load), and four repositories made by `tests/vcs_fixtures/export_scenarios.sh` (`made`: three records with an intent that has a session, a model and an issue, quotes, a backslash and a non-ASCII word, one with no intent, one at time 0, a file, an executable, a link and a directory, and a branch; `mixed`: `plain.git` imported and a change made on top of an imported one; `empty`: no change; `headonly`: HEAD detached at the newest change and no branch), the exported directory is equal to the Rust command's **file for file**, with the `cksum` of each (21 directories, `tests/vcs_fixtures/golden_export/`, made by `make_export_golden.sh` with the Rust command), and the document and the exit status are the Rust ones. They include a non-UTF-8 commit (the hex form of `Bytes`), a commit that does not render as itself, a commit with a `gpgsig`, a ref delta, a packed repository, remote-tracking refs, a detached HEAD, two alternates. The refusals: no directory and two directories (the document equal), no repository (equal), a directory that cannot be made (exit 3, `io-error`), a change missing from the store (`object-missing`, exit 1), a change of three parents (`object-corrupt`, exit 1); the last three are compared by tag and exit status (the Rust sentence carries the id or the OS's words). `--dry-run` writes no directory and its document is equal (as a set of lines, see below). `tests/commands/vcs_repo.sh`, section `== export-git`, runs all of it with the command in cancho: 81 checks, the transcript is 1,093 lines. *The real repositories:* `cancho-forge` imported natively then exported: **233 commits, 2,052 objects, 2,431 entries, `diff -r` equal to the Rust export, `git fsck --strict` passes, `git rev-list --all` equal to the source's 233, `git for-each-ref` equal (112 refs, the source's `refs/remotes/origin/HEAD`, a symbolic ref, is not imported, as §16 said)**; `cancho` (1,669 commits): **29,680 objects written, 30,206 files, `diff -r` equal to the Rust export, `git fsck --strict` passes, `rev-list --all` equal (1,669), `for-each-ref` equal (524)**. *Time and memory* (one run each, this machine; the import is §18's): `cancho-forge` **0.71 s native, 0.99 s Rust**; `cancho` **18.5 to 19.2 s native (42 MB), 10.9 s Rust (36 MB)**. So the export is faster than Rust on the small history and **about 1.7 times slower on the large one**: the store keeps each commit's tree as one flat text of 20,000 lines (about 2 MB) and the export reads it, finds each directory's range, and hashes every git tree of it again for each commit (Rust does the same work over a parsed `Tree`). 5.6 s of the 18.5 are system time (reading those texts: 1,669 of about 2 MB, an estimate and not a measurement). Two things tried to shorten it did nothing: computing each line's end once in the grouping loop (18.5 s before and after) and a one-`stat` test for an object that is there (18.9 s); the second was taken out again. Not done, and where the time would come from: keeping the git name of a subtree whose lines are unchanged since the last commit. It was left because 19 s for a 1,669-commit history is not the cost of this command's next slice, and a cache keyed by a subtree's text is a change to measure on its own.

**Mutation tested:** 44 changes (the stored-block header, the length complement, the Adler-32 byte order, the `parent` and `committer` words, the intent trailer, the empty-input case, the hex digit, the chunk boundary at 65,535; the table's number and id; the directory mode, the tag of a commit that has its name, the zero tree of a dry run, three trailer labels, the separators and the sign of the author's time, the `git` member, the `remotes` prefix, HEAD as a tip, the `ref:` text, the `refs/tags` directory, the comparison, the `equal` count, the pushing of parents, the visited test, the existence test of an object, the count of objects written, the refs' lines, the message of the argument check, the routing, the hex digits of two files and the hex decoding, the cut of a tree row's mode, the dry-run test of the refs, two checks of a change and the check of a tree): **36 caught**. Eight survived: four are **equivalent** (the visited test `< 2` against `< 3`, since a node popped as "expand" is never in the state in between; a cache of blobs and a cache of trees turned off, which only costs time; a slice `[0..len - 0]` I wrote as a mutant of nothing); four are checks **no fixture reaches**: the change with a valid hash but the wrong types in a part (`vcschange.well_typed`, tested in its own module and used here as Rust's `Change::load` is), the same check made a second time while writing the commits (it cannot fail after the first pass accepted the change), the failure code of the same, and `vcsobj.tree_status` on a tree that hashes right and is not a tree (the store cannot be made to hold one without writing an object by hand). Two of the 36 were found alive by the first run and killed after it: the 65,535 boundary (the unit test `test_a_block_of_exactly_the_longest_length_is_the_last`) and HEAD as the only way to a change (the scenario `headonly`); the refusal of `odd` with its octopus branch was added because a mutant of the first check of a change turned out to be unreachable, and it kills the mutant of the second.

**What differs from the Rust command, and is seen.** (1) **The list of commits that do not come back as they were** (`mismatches`) is in the order of the `gitmap` (sorted); the Rust command walks a hash map, so two or more are in no fixed order, and the test compares such a document as a set of lines. (2) **The sentence of a refusal for `object-corrupt`, `object-missing` and `io-error`** is the one `clivcsout.sentence` has (§17 says why); the tag and the exit status are the Rust ones. (3) **A git directory under a link**: the path is made absolute and walked from `/` without following links, as `init` does (§17); the Rust command's `create_dir_all` follows them. A relative path from a current directory the shell reports through a link (macOS's `/var`) works, since the current directory is the real one. (4) The temporary file of an object is made in its own directory (`put_whole`: `NAME.tmp-0`, then a rename) and not in `objects/tmp`, which is made and left empty; the files that are left, their contents and their modes (`644`; the directories `755`) are equal. (5) The Rust command writes the git files without a sync (`sync` is off "for derived data") and so does this one. (6) What the Rust command would do with a tree that is not in the order of its paths (it sorts) is refused here as `object-corrupt` by `vcsobj.tree_status`; the store as written by `import-git`, `record` and `apply` never has one.

**Where the Rust is now.** Nothing of `cancho vcs` goes to the Rust command: `init`, `log`, `show`, `branch`, `status`, `restore`, `switch`, `apply`, `unlock`, `record`, `revert`, `diff`, `blame`, `verify`, `import-git` and `export-git` are native, and `publish`, `sync`, `resolve`, `lock` and `fetch` were before them. `cancho-vcs` (about 5,300 lines) and `crates/cancho/src/vcs_*.rs` have no caller the standalone compiler needs; they are the oracle of the goldens and go with the crates (§5 of `removing-rust.md`, phase 5). #773 and #774 wait, as decided, until the Rust compiler is removed.
